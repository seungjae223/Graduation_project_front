# 추가 공통 저장 훅 검사

Root가 추가 위임한 `src/utils/usePlaceSaving.js`, `useFolderSavedPlaces.js` 및 새 테스트만 수정했다. API, Context, `useReadQuery`, `useMutationTask`는 변경하지 않았다.

## 확인하고 수정한 결함

1. 저장된 장소의 폴더 매핑 조회 중 다른 장소를 누르면 기존 조회가 계속 진행되는 동안 `target`이 새 장소로 바뀌었다. 첫 장소 제거 요청과 표시 대상이 혼합되는 경쟁 조건을 테스트에서 재현했다. 매핑 조회부터 첫 액션 완료까지 동기 선택 잠금과 응답 소유권을 적용하고 이 시간을 `busy/blocked`에 포함했다. 장소 ID 판별은 기존 공통 `savedPlaceId`를 재사용한다.
2. 이전 계정의 폴더 GET 응답이 늦게 도착하면 이미 AbortSignal이 취소되었어도 해당 폴더의 후속 장소 조회 함수를 시작했다. 계정 전환 테스트에서 재현했다. 첫 조회 전 및 첫 await 직후 취소를 검사하여 후속 조회를 시작하지 않도록 했다. 이미 진행된 요청에 대한 취소/응답 방어는 기존 공통 조회 훅을 유지한다.

## 수행 검사

- `src/utils/placeSaving.test.jsx`: 1 suite / 12 tests 통과. 로그 `auth-place-saving-tests.log`.
- 두 저장 훅과 테스트의 기존 ESLint 통과. 로그 `auth-place-saving-lint.log`. Browserslist 연령 경고만 있으며 패키지 업데이트는 하지 않았다.
- 두 폴더 중 선택 폴더만 제거한 후 다른 폴더와 공통 저장 상태 유지.
- 매핑 조회 실패 시 DELETE/POST를 실행하지 않고 기존 저장 상태 유지.
- 저장/삭제 응답 유실 후 기존 read-back으로 반영을 확인하고 자동 재전송하지 않음.
- 반영을 확인하지 못하면 완료로 표시하지 않고 잠금 유지; 실제 400 실패 후에는 명시적 재시도 허용.
- 동시에 두 번 저장을 선택해도 쓰기는 1회 실행.
- 매핑 조회 중 다른 장소 클릭은 기존 대상을 바꾸지 않음.
- 이전 계정의 늦은 쓰기는 새 계정의 선택/모달/저장 상태를 바꾸거나 조회하지 않음.
- 부분 실패 폴더만 마지막 확인 기록을 유지하고 성공한 빈 폴더는 비움.
- 정상 빈 폴더 목록은 오래된 공통 저장 기록을 실제로 비움.
- 늦은 이전 계정 목록은 후속 장소 조회를 시작하지 않고 새 계정의 목록·Context를 덮어쓰지 않음.

실제 브라우저·서버·화면 크기 검증은 Root 통합 결과와 별도로 보고해야 한다. 운영 사용자 데이터에 대한 저장/삭제를 실행하지 않았으며 검증 서버도 시작하지 않았다.
